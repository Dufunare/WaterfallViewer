## 0. 文档说明

这是一份面向“真正开始做项目”之前的项目文档。它不追求把所有实现细节一次性锁死，而是先把以下几件事说清楚：

1. 这个项目**为什么值得做**。
2. 这个项目**到底要解决什么问题**。
3. 这个项目**当前做什么，不做什么**。
4. 这个项目**从哪条主链开始启动最合理**。
5. 后续如果你想加功能，**应该沿着什么方向扩展**。

本项目当前的关键变化点是：

- 前端框架已经从原先讨论中的 React，更新为 **Vue**。
- 项目已具备 Tauri 工程骨架，可以直接从“最小闭环”开始推进。
- 当前实现策略不是“先做一个大而全的媒体库”，而是先做“**单目录会话式浏览**”的本地媒体查看器。

## 1. 项目一句话定位

**WaterfallViewer 是一个面向本地文件系统的轻量级桌面多媒体浏览器，它通过递归扫描和连续媒体流视图，把分散在多层文件夹中的图片、视频、音频重新组织为可滚动、可预览、可过滤的浏览体验。**

换句话说，它不是在替代文件管理器的所有职责，而是在补上文件管理器最不擅长的一块：

> **跨层级媒体的连续浏览体验。**

---

## 2. 为什么要做这个项目

传统文件管理器是“以目录树为中心”的工具。  
这种设计适合管理文件，但不适合做以下事情：

- 连续浏览一个根目录下所有深层媒体资源。
- 快速回看某个阶段积累的大量照片、视频片段和录音。
- 把素材目录当成“视觉流”而不是“树形文件夹”来浏览。
- 在浏览时同时兼顾性能、低内存和大规模目录的可用性。

### 典型痛点

1. **层级打断浏览**
   - 用户的心理模型是“我想连续看这一批内容”，不是“我要先点开 9 个子文件夹”。

2. **预览效率低**
   - 传统文件管理器对混合媒体的连续预览体验很差，经常需要来回切换。

3. **跨格式浏览割裂**
   - 图片、GIF、视频、音频经常要靠不同预览方式，难以放在同一个连续视图中。

4. **海量资源下体验不稳定**
   - 如果前端直接完整加载图片再测尺寸，或者渲染全量 DOM，很容易卡顿、跳动、内存上升。

5. **现有替代方案不合适**
   - 商业相册软件往往过重、缓存庞大、建库流程长。
   - 轻量查看器又往往只适合单张、单目录或小规模浏览。

## 3. 项目愿景

WaterfallViewer 的长期愿景不是做成一个“全能资产管理系统”，而是先成为一个：

- 打开快
- 本地优先
- 低认知负担
- 跨层级连续浏览体验好
- 后续可逐步增强到多媒体与缓存能力

的桌面媒体查看器。

### 愿景拆解

#### 3.1 用户感知层

用户选中一个目录后，能快速看到其中真正重要的东西：媒体内容本身。

#### 3.2 工程目标层

前端负责展示和交互，Rust 负责扫描与重计算，两边边界清晰，可持续扩展。

#### 3.3 迭代节奏层

先打通最小闭环，再逐步补齐：

- 过滤器
- 视频 / 音频
- 缩略图缓存
- 虚拟滚动
- 原生集成

## 4. 目标用户与典型场景

| 用户类型                   | 典型行为                                            | WaterfallViewer 的价值                         |
| -------------------------- | --------------------------------------------------- | ---------------------------------------------- |
| 创作者 / 设计师            | 从复杂素材树里快速浏览参考图、草图、片段            | 把目录树展平成视觉流，减少反复点开文件夹的成本 |
| 旅行 / 留学 / 生活记录用户 | 回看照片、Vlog 片段、录音，按记忆而不是按文件夹浏览 | 形成沉浸式连续回顾体验                         |
| 本地媒体重度用户           | 不想用云相册或重型媒体库                            | 本地优先，即开即用，缓存可控                   |
| 临时会话型用户             | 只是想快速浏览某个目录下有什么                      | 不强迫建库，不引入额外管理负担                 |

### 典型场景举例

#### 场景 A：素材整理

用户有一个 `references/` 根目录，下面按主题、年份、来源分了很多层子目录。  
他真正想做的是“看一遍所有参考图”，而不是逐层打开。

#### 场景 B：旅行回顾

用户有一个 `Swiss_Exchange/` 目录，里面按日期、城市、设备分了很多子目录。  
他真正想做的是“一路看下去，像翻相册一样回顾”。

#### 场景 C：轻量级本地媒体库

用户不想导入 Lightroom、相册软件，也不想为了快速浏览建一个长期数据库。  
他想要的是：选目录，马上看，关掉就结束。

## 5. 项目定位与边界

这个项目当前的定位是：

> **本地媒体浏览器**，不是全能文件管理器，也不是完整的数字资产管理系统。

### 当前明确做的事情

- 递归扫描指定根目录。
- 提取媒体元数据。
- 统一展示为连续媒体流。
- 支持至少图片主链的浏览与预览。
- 后续支持多媒体混合流与缓存增强。

### 当前明确不优先做的事情

- 批量重命名
- 复制 / 移动 / 删除工作流
- 标签系统
- 长期数据库索引
- 云同步
- 多用户协作
- 复杂编辑能力
- 一开始就做完视频 / 音频的全部高级能力

### 为什么要这样收边界

因为这个项目真正有价值的地方在于：

- **跨层级浏览**
- **布局与渲染性能**
- **前后端职责清晰**
- **本地文件系统体验**

如果一开始就同时做：

- 管理
- 索引
- 编辑
- 同步
- 播放器高级能力

项目复杂度会快速失控。

## 6. MVP 与当前第一闭环

当前最重要的不是把所有功能列全，而是明确**第一条必须跑通的主链**。

### 6.1 第一闭环目标

用户操作路径：

1. 打开应用。
2. 点击“选择文件夹”。
3. 选择一个包含若干图片的目录。
4. 在 1~3 秒内出现图片流。
5. 页面可以滚动。
6. 点击任意图片，可打开预览。
7. 关闭预览后仍能继续浏览。

### 6.2 第一闭环工程标准（Definition of Done）

- 不使用假数据。
- 必须经过 Tauri IPC。
- 必须有独立布局函数。
- 前端不自己读取图片尺寸。
- Rust 负责扫描和宽高返回。
- 必须在真实目录上跑通，不是只有“理论代码”。

### 6.3 为什么第一闭环只先做图片

因为图片链路已经足够覆盖项目最重要的几件事：

- 目录选择
- 递归扫描
- 元数据读取
- IPC 通信
- 布局计算
- 图片显示
- 预览开关

只要这条链真正打通，后面再加：

- 视频
- 音频
- 缩略图
- 虚拟滚动强化
- 缓存

就会稳很多。

## 8. 产品核心体验原则

### 8.1 本地优先

目录就是数据源，不强迫用户建立外部媒体库。

### 8.2 先看到，再精细化

先让用户看到结果，再逐步增强过滤、播放器、缓存等能力。

### 8.3 布局稳定

媒体资源异步加载时，必须有正确占位，不能严重跳动。

### 8.4 滚动流畅

海量媒体浏览必须从架构上控制 DOM 数量与资源请求量。

### 8.5 浏览连续

预览打开、关闭、切换时，尽量保留原浏览上下文。

### 8.6 重活后置

重 I/O、重解析、重 CPU 计算应由 Rust 负责，不下放给前端。

## 10. 当前风险与关键假设

### 10.1 前端框架经验不足

你目前还没有系统使用过前端框架，因此：

- 组件拆分
- 响应式状态
- 页面级状态组织
- 布局与渲染边界

都会在项目中边做边学。

**对策：**  
不要上来就追求完整生态和高级模式，先把 Vue 当成“更适合组织页面的方式”来用。

### 10.2 Rust 仍在学习中

Rust 会带来一些门槛：

- Result / Option
- struct / enum
- 文件系统操作
- 模块拆分
- 序列化

**对策：**  
第一阶段只学到足够支撑图片扫描与宽高返回即可。

### 10.3 视频 / 音频复杂度明显更高

图片只是读尺寸；视频 / 音频会涉及：

- 时长
- 首帧
- 封面
- 更重的解码路径

**对策：**  
不把视频 / 音频绑定到第一闭环。

### 10.4 大目录性能差异会很大

真实用户目录可能存在：

- 文件量大
- 层级深
- 磁盘慢
- 文件损坏
- 命名混乱

**对策：**  
第一阶段先保证边界正确，后续再用样例目录做基准测试。

## 11. 成功标准

### 第一层成功：主链打通

能够从真实目录中扫描出图片，返回前端，并稳定显示与预览。

### 第二层成功：结构可维护

不是“能跑但全写在一个文件里”，而是初步具备明确层次和改动入口。

### 第三层成功：可继续扩展

后续新增过滤器、视频 / 音频、缩略图时，不需要推倒重来。

## 12. 当前推荐的阶段推进方式

### P0：最小闭环

- 图片目录选择
- Rust 扫描 + 宽高返回
- Vue 渲染图片流
- 点击预览并关闭返回

### P1：图片浏览稳态版

- 错误处理
- 空状态
- 结构整理
- 基础过滤 / 排序
- 滚动位置保持

### P2：混合媒体接入

- 视频 / 音频识别
- 时长等元数据
- 统一卡片占位
- 类型过滤器增强

### P3：沉浸式查看增强

- 键盘导航
- 图片缩放与拖拽
- 视频播放
- 音频控制

### P4：性能与缓存强化

- 缩略图
- 任务队列
- 取消扫描
- 虚拟滚动强化
- 大目录稳定性优化

### P5：原生集成与产品化

- 打开所在目录
- 系统默认打开
- 图标 / 打包 / 权限打磨

## 13. 术语表

| 术语             | 含义                                               |
| ---------------- | -------------------------------------------------- |
| 根目录           | 用户主动选择、作为当前会话扫描起点的目录           |
| 会话式浏览       | 针对某次目录选择进行即时浏览，而不是先建长期数据库 |
| 媒体项 MediaItem | 扫描得到的单个可展示文件记录                       |
| 布局引擎         | 根据媒体尺寸与容器参数计算坐标的纯算法层           |
| 虚拟滚动         | 只渲染视口附近节点、控制 DOM 数量的机制            |
| 预览层 / Viewer  | 点击媒体项后进入的大图 / 播放界面                  |
| 骨架占位         | 在真实资源加载前，用已知尺寸提前撑开的占位模块     |

## 14. 当前版本最重要的一句话

**WaterfallViewer 现在不是“做全功能产品”的阶段，而是“把最值钱的主链做通”的阶段。**

只要你始终围绕这一点推进：

- 不做假数据捷径
- 不让前端接管 Rust 的工作
- 不把布局算法写死在组件里
- 不同时并行十个中后期功能

这个项目就会非常适合你当前阶段的成长路径。
