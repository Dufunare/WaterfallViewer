## 1. 项目概述

WaterfallViewer 是一款面向本地文件系统的轻量级桌面多媒体查看应用。它的核心目标不是替代传统文件管理器的全部能力，而是专门解决“深层目录中的媒体文件很难连续浏览、预览效率低、上下文被文件夹层级切碎”的问题。

项目将通过递归扫描、媒体元数据抽取、虚拟瀑布流布局和沉浸式查看模式，把分散在多层文件夹中的图片、视频、音频重新组织成一条可连续滚动、可过滤、可预览的视觉流。用户不需要逐层点开目录，也不需要等待重型相册软件建立庞大的数据库，就能快速看到自己在某个根目录之下真正拥有的素材全貌。

**一句话定位**
打破文件夹层级对本地媒体浏览的阻隔，让用户以接近相册流和素材库的体验，重新浏览与整理本地多媒体内容。

## 2. 项目要解决的问题

- 传统文件管理器以目录树为中心，适合管理文件，却不适合连续浏览跨层级媒体。
- 本地素材往往混合了图片、GIF、视频、录音，预览方式割裂，用户需要在多个应用或多个视图之间反复切换。
- 面对数量较多的媒体文件时，前端直接全量渲染或完整加载原始资源，极易引起卡顿、内存上涨和布局跳动。
- 个人记忆或创作素材通常按照年份、地点、主题被分散在多层子目录中，用户的心理模型是“连续回看”而不是“逐层进入文件夹”。
- 商业相册软件往往过重、过度索引、缓存庞大；而简单图片查看器又无法处理跨层级、多格式和海量浏览场景。

## 3. 目标用户与典型场景

| 用户 / 场景 | 典型动作 | WaterfallViewer 提供的价值 |
| --- | --- | --- |
| 创作者整理参考素材 | 选择一个包含大量子文件夹的素材根目录，快速浏览其中所有图片和视频。 | 把文件夹树“展平”为连续媒体流，减少来回点开目录的认知切换。 |
| 旅行 / 留学 / 生活记录回顾 | 在一次浏览中连续查看照片、Vlog 片段与录音，不希望被日期文件夹打断。 | 以更接近时间轴与相册的方式回顾本地记忆，支持沉浸式预览和快速切换。 |
| 轻量级本地素材库 | 不想依赖云服务，也不想安装臃肿相册软件。 | 本地优先、即开即用、缓存可控，强调轻量与低内存占用。 |
| 临时会话式浏览 | 只想查看某个根目录下当前有哪些媒体，不想长期维护数据库。 | 以“单目录会话”为起点，先解决浏览与预览，不强迫用户建立媒体库体系。 |

## 4. 产品定位与范围边界

本项目的目标是成为“本地媒体浏览器”，而不是“全能文件管理器”或“完整数字资产管理系统（DAM）”。它强调的是浏览效率、连续体验和资源轻量化，而不是复杂的整理、标记、同步和协作。

| 维度 | 本项目定位 | 当前不作为优先目标 |
| --- | --- | --- |
| 文件管理 | 提供基础浏览与打开能力，必要时可跳转系统默认行为。 | 不在 MVP 中实现复杂的复制、移动、批量重命名、回收站管理。 |
| 媒体库 | 优先做“单目录会话浏览”，减少建库门槛。 | 不在第一阶段做长期索引数据库、标签体系、多人协作。 |
| 云能力 | 以本地文件系统为基础，强调本地优先与启动快。 | 不在近阶段引入云同步、在线分享或远程访问。 |
| 编辑能力 | 聚焦查看、预览、过滤、切换。 | 不在早期加入复杂图片编辑、视频剪辑、波形编辑。 |

## 5. MVP 功能范围

| 功能项 | MVP 要求 | 备注 |
| --- | --- | --- |
| 深度递归扫描 | 必须具备 | 用户选择根目录后，自动扫描全部子文件夹并提取支持的媒体文件。 |
| 媒体混合流呈现 | 必须具备 | 至少统一处理图片、视频、音频三类媒体的列表表现；第一闭环可先只做图片。 |
| 纵向瀑布流布局 | 必须具备 | 第一阶段优先实现固定列宽、按比例计算高度的纵向模式。 |
| 横向 justified 布局 | 建议后续加入 | 价值很高，但实现复杂度高于纵向模式，适合作为第二阶段增强。 |
| 虚拟滚动 | 属于主架构要求 | 不是后期优化，而是支撑海量目录浏览不卡的必要条件。 |
| 沉浸式预览 | 必须具备 | 点击媒体项打开预览，支持关闭后回到原滚动位置。 |
| 键盘切换 | 应在中期加入 | 图片 / 视频 / 音频预览中的上一项、下一项切换。 |
| 实时过滤器 | MVP 可先做基础版 | 至少支持按媒体类型显示 / 隐藏；复杂排序和高级过滤可后置。 |
| 缩略图缓存 | 推荐纳入第二阶段 | MVP 可先直接展示原图或临时资源，后续再做持久化缓存。 |

## 6. 核心体验原则

- **本地优先**：用户选择的目录就是数据源，不强迫建立外部媒体库。
- **先看到，再精细化**：优先让用户尽快看到结果，而不是先做重型准备工作。
- **布局稳定**：媒体资源异步加载时，必须提前保留正确占位，避免页面跳动。
- **滚动流畅**：海量项目下 DOM 数量和资源请求都应被严格控制。
- **浏览连续**：预览打开、关闭、切换时，要尽量保留上下文与位置记忆。
- **职责清晰**：前端负责呈现和交互，Rust/Tauri 负责扫描、解析和重活。

## 7. 典型用户主流程

1. 用户打开应用，进入空状态首页。
2. 点击“选择文件夹”，通过原生对话框选中某个根目录。
3. 应用开始扫描目录，并在界面上显示扫描进行中的反馈；第一批结果尽快出现。
4. 前端按布局规则把媒体项放入瀑布流，用户可以立即滚动浏览。
5. 用户通过过滤器选择仅看图片 / 视频 / 音频，或保留全部混合视图。
6. 点击任意媒体项进入沉浸式预览；退出预览后回到原来的浏览上下文。

## 8. 非功能目标与体验基线

| 指标 | 目标描述 | 说明 |
| --- | --- | --- |
| 启动响应 | 冷启动保持秒级可感知响应 | 用户打开应用后应尽快进入可操作界面。 |
| 首屏反馈 | 选择目录后尽快看到扫描反馈与首批内容 | 第一闭环建议在 1~3 秒内让一个普通图片目录出现图片流。 |
| 滚动性能 | 长列表滚动中避免明显掉帧与主线程卡死 | 必须通过虚拟列表、懒加载和并发控制来保证。 |
| 内存稳定 | 长时间浏览时内存不随滚动无界增长 | 避免完整解码、避免全量 DOM、及时释放不在视口中的资源。 |
| 布局一致性 | 异步图片加载不应引发顺序错乱或明显跳动 | 前端只能消费后端返回的宽高信息，不再自行探测尺寸。 |
| 安全边界 | 仅访问用户明确授权的目录 | 遵循 Tauri 的权限和能力控制，不默认开放任意路径访问。 |

## 9. 当前阶段的关键假设与风险

| 事项 | 当前判断 | 对策 / 后续动作 |
| --- | --- | --- |
| 前端框架经验不足 | 实现者尚未系统接触 React 等前端框架。 | 文档和大模型辅助下，优先掌握组件、状态、事件和基础布局，不追求复杂生态。 |
| Rust 仍在学习 | 后端实现需要控制难度，避免一开始引入过多高级抽象。 | 第一闭环仅做图片扫描与宽高返回；并发、缩略图缓存等逐步引入。 |
| 视频 / 音频元数据复杂 | 不同格式的时长、首帧、封面获取方式差异大。 | 在图片主链跑通后，再独立评估视频与音频的元数据方案。 |
| 大目录性能差异大 | 不同磁盘、不同文件系统、不同目录深度表现会明显不同。 | 先以“体验稳定、接口可扩展”为目标，随后再做 Benchmark 和瓶颈分析。 |
| 路径与资源展示方式 | 本地路径如何安全转换为前端可展示资源，需结合 Tauri 能力实现。 | 在架构文档中固定“由 Rust 或受控桥接层提供可展示资源”的原则。 |

## 10. 成功标准（以当前项目阶段衡量）

- **第一闭环成功**：用户能真实选择一个图片目录，通过 Tauri IPC 获得 Rust 扫描结果，并在前端看到可滚动的图片流。
- **主链路打通**：从目录选择、递归扫描、元数据返回、布局计算、图片显示到预览关闭，整条链路可运行且不依赖假数据。
- **边界清晰**：前端不负责图片尺寸探测，布局函数独立存在，Rust 负责扫描与尺寸元数据，后续可以在此基础上扩展视频 / 音频。
- **文档可维护**：后续任何新需求都能快速判断应修改哪一层、哪一类模块，而不是把逻辑堆在同一个组件或命令里。

## 11. 核心术语表

| 术语 | 含义 |
| --- | --- |
| 根目录 | 用户主动选择、作为本次扫描起点的目录。 |
| 会话式浏览 | 针对某次选择的目录进行即时扫描和浏览，而不是长期维护数据库索引。 |
| 媒体项（MediaItem） | 扫描后得到的单个可展示文件记录，通常包含路径、类型、宽高、时长等字段。 |
| 布局引擎 | 把媒体数据计算为屏幕坐标和尺寸的纯算法层。 |
| 虚拟滚动 | 只渲染视口附近的项目，并用总高度 / 总宽度维持真实滚动空间的机制。 |
| 沉浸式预览 | 点击媒体项后进入更大的查看 / 播放界面，并支持返回继续浏览。 |
| 骨架占位 | 在真实媒体资源尚未加载前，用已知尺寸先撑开布局的占位模块。 |
