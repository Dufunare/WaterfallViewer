# WaterfallViewer 架构文档

**面向实现与后续改动的分层设计说明（草案 v0.1）**

| 属性 | 内容 |
| --- | --- |
| **项目阶段** | 预启动；实现细节尚未全部敲定 |
| **文档目的** | 明确分层边界、模块职责、IPC 契约和未来变更入口 |
| **推荐读者** | 主实现者、未来协作者、后续维护者 |
| **架构基线** | Tauri + Rust 后端，React + TypeScript 前端 |
| **更新时间** | 2026-03-25 |

## 文档说明
本文件优先定义“职责边界”和“改动入口”，而不是把所有库和实现细节一次性锁死。后续如果技术选型发生调整，只要边界不变，整体架构依然成立。

---

## 1. 架构目标与设计原则

- 前端只负责渲染、交互和视图编排，不承担大规模文件 I/O 与媒体元数据探测。
- Rust/Tauri 负责目录扫描、元数据提取、并发调度、缩略图和其他重计算工作。
- 布局层保持为可独立测试的纯算法层，避免与具体 UI 组件和 DOM 结构强耦合。
- 单目录会话浏览优先于长期数据库索引，先把主链路跑通，再逐步增强。
- 所有跨层通信尽量通过稳定接口进行：前端组件不直接“碰系统”，后端服务不“理解页面长什么样”。
- 在项目早期允许实现简化，但不能破坏后续升级到增量扫描、虚拟滚动和缩略图缓存的路径。

**核心原则**
上层使用下层，下层不要知道上层。UI 负责“画”，编排层负责“调度”，布局层负责“算坐标”，Rust 应用服务层负责“做业务”，基础设施层负责“碰系统”。

## 2. 总体分层模型

```text
表现层（UI / Components）
        ↓
交互编排层（Hooks / Store / Page Controller）
        ↓
布局与视图模型层（Layout Engine / Virtual Window）
        ↓
领域与应用服务层（Rust Services / Tauri Commands）
        ↓
基础设施与平台层（File System / OS / Crates / Tauri Capability）
```

| 层级 | 主要职责 | 输入 / 输出 | 不应该做什么 |
| --- | --- | --- | --- |
| 表现层 | 渲染界面、接受点击 / 滚动 / 键盘输入、显示空状态和错误状态。 | 输入：可渲染状态；输出：用户动作。 | 不直接扫描文件、不自行测图片尺寸、不编写重型业务逻辑。 |
| 交互编排层 | 把用户动作翻译为系统请求，把系统数据整理成 UI 可直接消费的状态。 | 输入：服务返回数据、布局结果；输出：页面状态和操作接口。 | 不直接碰文件系统，不把全部计算都塞进组件内部。 |
| 布局与视图模型层 | 根据媒体项、容器尺寸、布局模式计算坐标、占位尺寸和可视窗口。 | 输入：MediaItem 列表、布局参数；输出：LayoutItem / VisibleSlice。 | 不关心 React 组件细节，不依赖 Rust 命令。 |
| 领域与应用服务层 | 目录扫描、媒体识别、元数据读取、任务控制、缩略图与缓存策略。 | 输入：目录路径、任务参数；输出：媒体数据、进度、错误、缩略图路径。 | 不嵌入页面语义，不为某个具体组件写特化逻辑。 |
| 基础设施与平台层 | 文件系统访问、三方 crate、原生能力、路径与权限、系统集成。 | 输入：应用服务的底层调用；输出：原始字节、路径、平台能力。 | 不决定业务规则，不关心是否是瀑布流或预览弹层。 |

## 3. 每一层应该做什么

### 3.1 表现层（Presentation / UI Layer）
负责内容呈现与用户输入。典型模块包括首页空状态、目录选择入口、媒体网格容器、媒体卡片、过滤器面板、预览层、播放控件和错误提示。

**这一层应该做：**
- 接收编排层提供的可直接渲染状态。
- 根据 LayoutItem 渲染卡片位置、尺寸和占位。
- 把点击、滚动、键盘操作回传给编排层。

**这一层不应该做：**
- 不调用文件系统 API。
- 不自行 `new Image()` 探测海量图片尺寸。
- 不持有复杂业务流程和跨模块状态机。

**后续改动提示：**
最常改动：视觉结构、交互样式、按钮文案、预览层 UI。

### 3.2 交互编排层（ViewModel / State Orchestration Layer）
负责把系统能力组织成页面能用的状态。可由 React hooks、store、controller 组成，是 UI 与业务能力之间的粘合层。

**这一层应该做：**
- 发起扫描、取消扫描、切换过滤条件、打开预览。
- 接收扫描结果后做筛选、排序、视图投影。
- 调用布局引擎并根据滚动位置计算当前可见内容。

**这一层不应该做：**
- 不直接做重 I/O。
- 不把布局算法写死在某个组件里。
- 不把所有全局状态都揉成一个巨型 store。

**后续改动提示：**
最常改动：状态字段、操作流程、过滤 / 排序行为、页面级交互逻辑。

### 3.3 布局与视图模型层（Layout Engine / View Projection）
项目中最需要保持独立的一层。它的职责是把一组媒体数据变成屏幕上的坐标、尺寸与可视切片，而不是负责真正渲染。

**这一层应该做：**
- 根据宽高比、列数、容器宽度计算纵向瀑布流坐标。
- 在后续阶段支持横向 justified 布局。
- 提供可视范围计算和 overscan 逻辑，服务虚拟滚动。

**这一层不应该做：**
- 不依赖 DOM 查询结果作为主要输入。
- 不直接访问 React state 或 Tauri 命令。
- 不关心用户是从按钮还是键盘触发了动作。

**后续改动提示：**
最常改动：布局模式、列数规则、可视窗口算法、导出布局复用。

### 3.4 领域与应用服务层（Rust Application / Domain Services）
承接真正的业务能力：递归扫描、媒体类型识别、头部信息解析、并发控制、缩略图与缓存等。

**这一层应该做：**
- 把目录扫描封装为稳定命令或事件流。
- 统一生成 MediaItem 所需元数据。
- 隔离底层 crate 与平台差异，对外暴露清晰接口。

**这一层不应该做：**
- 不嵌入 UI 语义，如“三列深色主题瀑布流”之类的命令。
- 不依赖 React 页面结构。
- 不把错误信息写成只有组件能理解的特殊格式。

**后续改动提示：**
最常改动：媒体解析策略、扫描批次、并发限制、缩略图与缓存能力。

### 3.5 基础设施与平台层（Infrastructure / Platform）
负责和操作系统、文件系统、Tauri 能力、第三方 crate 直接打交道。这里允许与平台高度耦合，但要尽量与业务语义解耦。

**这一层应该做：**
- 读取目录、打开文件、读取头部字节。
- 封装图片 / 视频 / 音频三方库的具体调用。
- 控制 capability、permission 和路径作用域。

**这一层不应该做：**
- 不决定扫描流程何时开始或结束。
- 不理解 UI 中的过滤面板或预览状态。
- 不把平台细节泄漏到上层调用方。

**后续改动提示：**
最常改动：底层库替换、平台兼容、权限模型、缓存路径。

## 4. 推荐模块划分
为了让项目后续更容易维护，建议在前端和 Rust 端都按职责拆模块，而不是按“页面文件堆积”或“所有命令塞到 main.rs”的方式开发。以下结构不是唯一解，但非常适合作为第一版工程骨架。

```text
src/
  app/
  components/
    folder-picker/
    media-grid/
    media-card/
    viewer/
    filters/
  hooks/
  stores/
  layout/
  types/
  utils/

src-tauri/
  src/
    commands/
      scan.rs
      thumbnail.rs
      preview.rs
    services/
      scanner/
      parser/
      thumb/
      cache/
      task_manager/
    models/
    main.rs
  capabilities/
  permissions/
```

| 前端模块 | 职责 | 备注 |
| --- | --- | --- |
| app / pages | 页面入口、应用壳、顶层布局。 | 控制页面骨架，不持有底层媒体解析逻辑。 |
| folder-picker | 目录选择入口与扫描触发 UI。 | 只负责交互入口，不负责真正扫描。 |
| stores / hooks | 会话状态、过滤条件、预览状态、滚动状态。 | 是 UI 与服务之间的编排层核心。 |
| layout | 瀑布流计算、可视窗口计算、骨架占位。 | 应尽量保持纯函数和可测试。 |
| media-grid / media-card | 瀑布流容器与单卡片表现。 | 只消费已计算的位置与尺寸。 |
| viewer | 沉浸式预览层与播放器控制。 | 独立于列表页，关闭后要能返回原上下文。 |
| filters | 媒体类型与排序 UI。 | 本身不决定如何扫描，只改变视图投影。 |

| Rust 模块 | 职责 | 备注 |
| --- | --- | --- |
| commands | 对外暴露 Tauri 命令 / 事件的薄接口。 | 只做参数校验、调用服务、返回结果，不堆积业务。 |
| services/scanner | 递归遍历目录、筛选候选文件。 | 可先从图片扫描开始，后续扩展媒体类型。 |
| services/parser | 读取头部、识别媒体格式、提取宽高 / 时长。 | 是“前端不自己读尺寸”的关键保障。 |
| services/task_manager | 管理扫描任务、取消、批次输出、并发限制。 | 第一闭环可简化，后续用于增量扫描。 |
| services/thumb | 缩略图生成与本地缓存。 | 建议第二阶段接入。 |
| services/cache | 缓存目录与命中策略。 | 与 thumb 或未来数据库能力配合。 |
| models | 统一 MediaItem、ScanProgress 等结构。 | 保证前后端协议稳定。 |
| capabilities / permissions | 限制窗口可用能力与目录作用域。 | 是 Tauri 2 安全模型的重要部分。 |

## 5. 关键数据模型
以下数据结构是建议基线，字段可以增减，但要尽量维持语义稳定。项目越早统一这些数据结构，后面就越不容易在前后端之间反复返工。

```typescript
type MediaKind = 'image' | 'video' | 'audio'

type MediaItem = {
  id: string
  path: string
  kind: MediaKind
  width?: number
  height?: number
  aspectRatio?: number
  durationMs?: number
  createdAt?: number
  modifiedAt?: number
  thumbPath?: string
  displaySrc?: string
  scanSessionId: string
}

type LayoutOptions = {
  mode: 'masonry-vertical' | 'justified-horizontal'
  columnCount?: number
  rowHeight?: number
  gap: number
  viewportWidth: number
}

type LayoutItem = {
  id: string
  x: number
  y: number
  width: number
  height: number
}
```

| 模型 / 字段 | 职责说明 |
| --- | --- |
| MediaItem.id | 在整个前端会话中唯一标识媒体项；不要直接把 path 当作唯一主键写死。 |
| MediaItem.path | 原始文件路径；用于打开系统默认应用、生成资源地址、创建缩略图缓存键。 |
| MediaItem.kind | 决定列表展示占位与预览方式。 |
| width / height / aspectRatio | 布局层最关键的数据；由 Rust 提供，前端只消费。 |
| durationMs | 视频 / 音频的重要元数据，列表与预览层都可能使用。 |
| thumbPath / displaySrc | 缩略图路径或可展示资源地址；设计上可以保留二者之一。 |
| scanSessionId | 把本次目录选择对应的数据会话隔离出来，便于取消扫描和重置状态。 |
| LayoutOptions | 保证布局引擎输入集中，避免在组件中散落各种 magic number。 |
| LayoutItem | 布局层输出的唯一坐标数据结构，导出功能后续也可复用。 |

## 6. IPC 契约设计
IPC 是前端与 Rust 的边界。接口应该围绕“业务动作”设计，而不是围绕组件事件设计。下表按‘第一闭环必须项’与‘后续增强项’给出建议。

| 接口 | 方向 | 阶段 | 说明 |
| --- | --- | --- | --- |
| scan_images(rootPath) | 前端 → Rust | 第一闭环必须 | 最小闭环可以先返回图片列表与宽高；目录规模较小时允许一次性返回。 |
| scan_media(rootPath, options) | 前端 → Rust | 后续增强 | 升级版统一扫描接口，支持图片 / 视频 / 音频与更多参数。 |
| cancel_scan(taskId) | 前端 → Rust | 第二阶段 | 用于中断长时间扫描任务。 |
| scan_progress | Rust → 前端事件 | 第二阶段 | 回传扫描进度、已发现数量、错误提示。 |
| scan_batch | Rust → 前端事件 | 第二阶段 | 按批次推送媒体项，降低大目录首屏等待时间。 |
| request_thumbnail(itemId) | 前端 → Rust | 第二或第三阶段 | 与懒加载结合，只在即将进入视口时触发。 |
| open_in_system(path) | 前端 → Rust | 后续可选 | 调用系统默认行为打开文件或所在目录。 |

**阶段性建议**
第一闭环为了降低复杂度，可以先采用“一次扫描，一次返回”的简单命令；但接口命名和数据结构要为未来的批次返回与事件推送留好升级路径。

## 7. 运行时主流程

### 7.1 目录扫描到列表渲染
1. 用户在前端点击“选择文件夹”。
2. 前端通过原生目录选择能力拿到根目录路径。
3. 编排层调用 Rust 命令发起扫描；如处于第一闭环，可直接调用 `scan_images`。
4. Rust 扫描器递归遍历目录，识别图片文件，并提取宽高等元数据。
5. Rust 返回 MediaItem 列表给前端；后续阶段可改为进度事件 + 批次事件。
6. 编排层将数据送入布局引擎，得到 LayoutItem 列表和总滚动高度。
7. UI 层只渲染视口附近项目，卡片组件根据宽高比显示占位或真实资源。

### 7.2 点击预览到返回浏览
1. 用户点击某个媒体项，UI 层把 itemId 交给编排层。
2. 编排层更新 viewer 状态，记录当前选中项与来源列表位置。
3. 预览层根据媒体类型选择图片查看器、视频播放器或音频播放面板。
4. 用户关闭预览时，列表层恢复到之前的滚动位置和过滤条件。

### 7.3 后续缩略图与懒加载流程
1. 列表中仅先渲染带尺寸占位的卡片。
2. 当卡片接近视口时，前端通过 Intersection Observer 触发资源加载。
3. 若缩略图已存在，则直接读取 thumbPath；否则发起缩略图请求进入后台队列。
4. 队列通过并发限制避免同时开启过多 CPU / I/O 密集任务。

## 8. 横切关注点

| 主题 | 当前要求 | 设计建议 |
| --- | --- | --- |
| 性能 | 万级目录下不能依赖全量 DOM。 | 虚拟滚动是主架构要求；宽高信息必须提前可用。 |
| 错误处理 | 扫描失败、权限不足、损坏文件不能直接让页面崩掉。 | Rust 返回结构化错误；前端提供局部错误提示与跳过机制。 |
| 安全 | 只访问用户明确选择的目录。 | 通过 Tauri capability / permission 控制访问面。 |
| 取消与重入 | 用户可能在扫描未完成前重新选目录。 | 引入 scanSessionId 与任务取消机制，避免旧结果污染新会话。 |
| 日志与排错 | 早期阶段需要快速定位是前端问题还是后端问题。 | 前端打印动作与状态变更；Rust 对扫描阶段和解析失败进行可读日志记录。 |
| 测试 | 布局和扫描逻辑应可独立验证。 | 布局层做纯函数测试；Rust 服务做单元测试和样例目录测试。 |

## 9. 改动时优先看哪里

| 需求变化 | 优先修改层 / 模块 | 可能联动 | 不应首先修改 |
| --- | --- | --- | --- |
| 新增排序规则（按时间、名称等） | 交互编排层 / store | MediaItem 字段可能需补充 createdAt 等。 | 不要先改 UI 卡片结构。 |
| 新增媒体类型 | Rust parser / models | 前端过滤器、预览层、卡片占位会联动。 | 不要让前端自己去猜媒体类型。 |
| 切换为横向 justified 布局 | layout 层 | UI 容器样式与设置面板会少量联动。 | 不要在 card 组件里硬写坐标算法。 |
| 引入缩略图缓存 | Rust thumb / cache 服务 | 前端只需多消费 thumbPath。 | 不要把缓存逻辑塞进 React 组件。 |
| 增加扫描进度条 | IPC 事件 + 编排层 | UI 只渲染状态。 | 不要在扫描器里直接调用前端 setState。 |
| 增加导出长图 / PDF | 布局层 + 独立导出服务 | 需要复用 LayoutItem 与 MediaItem。 | 不要依赖当前虚拟列表 DOM 截图。 |
| 增加系统右键集成 | 基础设施 / 平台层 | 命令层与权限配置可能联动。 | 不要污染布局或 viewer 逻辑。 |

## 10. 当前仍未敲定的设计点

| 议题 | 当前建议 | 可延后到何时决定 |
| --- | --- | --- |
| 前端状态管理方案 | 前期可用简单 hooks 或轻量 store；不要一开始上过重框架。 | 第一闭环完成前都可不锁死。 |
| 虚拟滚动实现方式 | 可以自写最小版本，也可选成熟库；核心是接口边界清晰。 | 在静态图片流跑起来之后。 |
| 视频 / 音频元数据方案 | 优先在图片主链稳定后再评估；不建议和第一闭环绑定。 | 图片浏览稳定后。 |
| 缩略图缓存持久化策略 | 第二阶段再做；第一闭环可先不持久化。 | 引入大目录和视频预览之前。 |
| 扫描结果回传模式 | 先允许小目录一次性返回，未来升级为批次事件。 | 当真实目录规模导致等待时间明显上升时。 |
| 资源展示路径策略 | 保持“后端负责可信路径，前端负责受控展示”的原则。 | 在具体实现展示链路时。 |
