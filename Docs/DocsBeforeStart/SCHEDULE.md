# WaterfallViewer 工作阶段与后续安排

**从第一闭环到后续版本迭代的实施路线（草案 v0.1）**

| 属性               | 内容                                                  |
| ------------------ | ----------------------------------------------------- |
| **文档目的**       | 把项目拆成可执行阶段，并给出每阶段的完成标准          |
| **当前最优先目标** | 跑通最小闭环：真实目录选择、Rust 扫描、前端渲染与预览 |
| **阶段规划原则**   | 先主链、后增强；先图片、后混合媒体；先可用、后优化    |
| **建议节奏**       | 按阶段验收，而不是所有功能并行推进                    |
| **更新时间**       | 2026-03-25                                            |

## 文档说明

本文件中的阶段不是绝对的“日历时间表”，而是“达到某种能力状态就可以进入下一阶段”的工程划分。每个阶段都要有明确输出和退出条件。

---

## 1. 开发总原则

- 任何阶段都先保证主链路可运行，再考虑做漂亮。
- 不使用假数据验证关键链路；从第一闭环开始就走真实 Tauri IPC。
- 每个阶段都保留可以演示的成果，避免长时间停留在“重构中”。
- 新能力尽量以不破坏既有边界的方式加入：前端不接管后端工作，布局层不被 UI 污染。
- 阶段完成标准要写清楚：什么算做完，什么故意留到下一阶段。

## 2. 阶段总览

| 阶段               | 目标                                             | 核心输出                                         | 退出条件                         |
| ------------------ | ------------------------------------------------ | ------------------------------------------------ | -------------------------------- |
| P0：最小闭环       | 打通真实目录选择、图片扫描、布局显示、预览关闭。 | 可运行的图片浏览主链。                           | 不使用假数据，前后端能完整跑通。 |
| P1：图片浏览稳态版 | 把图片浏览从“能跑”提升到“可维护、可继续扩展”。   | 更清晰的状态管理、错误处理、基础过滤与滚动稳定。 | 主链稳定、结构清晰。             |
| P2：混合媒体接入   | 把视频 / 音频纳入统一流。                        | 多媒体占位、时长等元数据、过滤器增强。           | 三类媒体都能被识别和展示。       |
| P3：沉浸式查看增强 | 预览层从基础放大图升级为完整查看器。             | 键盘切换、视频播放、音频控制、上下文保持。       | 浏览与预览体验连贯。             |
| P4：性能与缓存强化 | 应对更大的目录和更重的媒体。                     | 缩略图、任务队列、取消扫描、内存更稳定。         | 大目录下体验显著改善。           |
| P5：原生集成与打磨 | 桌面产品化与系统能力增强。                       | 右键打开、打开所在目录、权限收敛、打包发布。     | 具备持续使用价值。               |

## 3. P0：最小闭环（当前第一优先级）

**阶段目标**
用最少功能跑通最关键的真实链路：选择目录 → Rust 扫描图片并返回宽高 → 前端独立布局 → 出现可滚动图片流 → 点击图片打开预览 → 关闭后继续浏览。

### 3.1 P0 的用户操作路径

1. 打开应用。
2. 点击“选择文件夹”。
3. 选择一个包含若干图片的目录。
4. 在 1~3 秒内出现图片流。
5. 页面可以滚动。
6. 点击任意图片，可打开预览。
7. 关闭预览后仍能继续浏览。

### 3.2 P0 的工程标准（Definition of Done）

- 不使用假数据。
- 必须经过 Tauri IPC。
- 必须有独立布局函数。
- 前端不自己读取图片尺寸。
- Rust 负责扫描和宽高返回。
- 图片目录在真实环境中可跑通，不是只在理论上有代码。

### 3.3 P0 范围内应该做的内容

| 模块      | P0 必做                                  | P0 不做 / 可后置                     |
| --------- | ---------------------------------------- | ------------------------------------ |
| 目录选择  | 打通原生目录选择，获取根目录路径。       | 复杂最近目录历史、收藏夹。           |
| Rust 扫描 | 递归扫描图片文件并返回路径、宽高。       | 视频 / 音频、批次事件、任务取消。    |
| 前端渲染  | 根据返回数据渲染图片流和骨架占位。       | 复杂过滤器、排序器、动画优化。       |
| 布局      | 独立实现纵向瀑布流函数。                 | 横向 justified 布局。                |
| 预览      | 点击图片打开大图预览，并能关闭返回。     | 键盘切换、缩放拖拽、媒体播放器。     |
| 性能      | 至少避免明显的全屏阻塞，保证小目录体验。 | 完整虚拟滚动与缩略图缓存的最终形态。 |

### 3.4 P0 建议拆成 6 个工作包

| 工作包              | 内容                                                 | 完成标志                                  |
| ------------------- | ---------------------------------------------------- | ----------------------------------------- |
| WP1：项目骨架       | 创建 Tauri + Vue + TypeScript 工程，确认能本地运行。 | 空页面可启动，前后端开发命令正常。        |
| WP2：目录选择 + IPC | 前端能选择目录，并成功调用一个 Rust 命令。           | 把选中的路径传到 Rust 并得到可见返回值。  |
| WP3：Rust 图片扫描  | 递归找出图片文件并提取宽高。                         | 返回 MediaItem 列表，前端能收到真实数据。 |
| WP4：独立布局函数   | 把图片宽高转换成瀑布流坐标。                         | 无需依赖组件即可独立测试布局结果。        |
| WP5：图片流渲染     | 按布局渲染图片列表，支持滚动。                       | 页面能展示真实图片流。                    |
| WP6：预览层         | 点击图片打开预览并关闭返回。                         | 关闭后保留浏览上下文。                    |

### 3.5 P0 的验收清单

- 可以现场演示从选择目录到看到真实图片的完整流程。
- 图片尺寸来自 Rust 返回，而不是前端自己探测。
- 布局函数不写在组件模板或页面脚本中，可以单独调用并输出坐标结果。
- 预览层打开 / 关闭逻辑独立，不会导致列表直接丢状态。
- 工程目录已经形成前端与 Rust 的基本拆分，而不是一团代码写在一个文件里。

### 3.6 P0 常见陷阱

- 一开始就把视频、音频、缩略图、虚拟滚动全部并行推进，导致主链路迟迟不闭合。
- 前端为了省事直接加载图片再读尺寸，破坏后续稳定占位和性能边界。
- 把布局算法直接写在 Vue 组件里，后续几乎无法复用和测试。
- Rust 命令返回的数据结构不稳定，导致前后端每改一次都要大范围返工。
- 为了“性能”过早做复杂并发，反而增加调试难度。

## 4. P1：图片浏览稳态版

当 P0 打通后，下一步不是立刻加入所有媒体类型，而是先把“图片浏览这条链”打磨到足够稳定，确保它能承接后续扩展。

| 目标               | 重点工作                                                | 退出条件                                 |
| ------------------ | ------------------------------------------------------- | ---------------------------------------- |
| 结构稳态化         | 整理 composables / store / commands / services 的边界。 | 目录结构清晰，代码不再全部堆在单一页面。 |
| 错误与空状态       | 处理目录为空、权限不足、损坏图片等情况。                | 错误不会导致应用直接崩溃。               |
| 基础过滤和排序     | 先加入简单排序、按图片类型过滤等。                      | 视图切换不会破坏主链。                   |
| 滚动与位置保持     | 预览关闭后滚动位置恢复更稳定。                          | 浏览上下文连贯。                         |
| 为批次扫描预留接口 | 即使暂不实现，也开始让协议支持未来升级。                | 不会锁死在难以扩展的全量返回设计。       |

## 5. P2：混合媒体接入

这一阶段的任务是从“图片浏览器”升级为真正的“多媒体流浏览器”。图片主链稳定之后，再逐步把视频和音频接进来。

| 能力         | 建议内容                                | 注意事项                                 |
| ------------ | --------------------------------------- | ---------------------------------------- |
| 媒体类型识别 | 统一识别 image / video / audio。        | 不要把类型判断逻辑散落到前端多个组件。   |
| 元数据扩展   | 补充视频 / 音频时长、视频分辨率等字段。 | 字段设计尽量兼容不同媒体类型。           |
| 占位模块     | 视频卡片、音频卡片使用统一风格占位。    | 列表层先关注连续浏览，不追求复杂播放器。 |
| 过滤器增强   | 支持按媒体类型显示 / 隐藏。             | 让过滤逻辑留在编排层，而不是卡片层。     |
| 展示链路     | 评估视频首帧、音频封面或默认占位策略。  | 这是复杂点，可以先做保守方案。           |

## 6. P3：沉浸式查看增强

| 目标         | 内容                                                    |
| ------------ | ------------------------------------------------------- |
| 图片体验增强 | 支持更完整的大图查看、缩放、拖拽、上一项 / 下一项切换。 |
| 视频播放     | 在预览层中加入基础视频播放控制。                        |
| 音频播放     | 在预览层中加入基础播放、暂停、进度反馈。                |
| 键盘与导航   | 支持 Esc 关闭、方向键切换、回到列表上下文。             |
| 交互统一     | 无论媒体类型如何，预览层都保持一致的开关和切换体验。    |

## 7. P4：性能与缓存强化

| 重点         | 为什么要做                                   | 建议方式                                   |
| ------------ | -------------------------------------------- | ------------------------------------------ |
| 虚拟滚动完善 | 真实目录规模上来后，必须严格控制 DOM。       | 把列表渲染限制在可视窗口与 overscan 区域。 |
| 缩略图缓存   | 原图 / 视频首帧直接展示成本过高。            | 引入 thumb 服务与本地缓存目录。            |
| 并发控制     | 缩略图或重型预览任务过多会压垮 I/O。         | 用队列与信号量限制同时进行中的任务数。     |
| 取消扫描     | 用户切目录时旧任务需要可中断。               | 给扫描任务加入 taskId 和取消机制。         |
| 基准测试     | 需要知道瓶颈在扫描、解析、渲染还是资源加载。 | 建立样例目录和基础 benchmark 场景。        |

## 8. P5：原生集成与产品化打磨

| 方向       | 内容                                                      |
| ---------- | --------------------------------------------------------- |
| 系统集成   | 打开系统默认应用、打开所在目录、未来右键菜单注册等。      |
| 安全与权限 | 整理 capability / permission 范围，只保留真正需要的能力。 |
| 设置与偏好 | 列数、间距、主题、默认预览行为等用户偏好。                |
| 打包发布   | 面向目标平台的安装包、图标、基本产品文案与说明。          |
| 可维护性   | 补齐文档、测试、日志和错误报告能力。                      |

## 9. 每个阶段都要同步维护的事项

- 更新文档：当数据结构、模块边界或阶段目标变化时，立即更新架构文档和技术清单。
- 记录决策：对库选择、路径策略、扫描模式等关键设计做简短决策记录。
- 保留演示素材：为每个阶段准备一个真实目录样本，便于回归测试。
- 控制复杂度：只在前一阶段稳定后引入下一阶段的重要新能力。
- 形成检查清单：每完成一阶段，明确列出“已完成 / 故意未做 / 下阶段承接项”。

## 10. 当前建议的实施顺序（简版）

1. 先把 Tauri 工程跑起来，确认本机环境稳定。
2. 先做目录选择 + IPC 验证，不要还没打通通信就先写大堆 UI。
3. 先让 Rust 扫描出图片路径和宽高，再写布局。
4. 先完成图片流和预览，再回头整理状态结构。
5. 图片主链稳定后，再引入过滤器、视频 / 音频、缩略图、性能强化。
6. 当项目真正进入可用状态后，再考虑原生集成和发布打磨。
